# 서명 기반 일정 등록

관리자 P가 지급 조건에 EIP-712 서명하면 지정 수령자 B가 `createScheduleWithSignature`로 등록합니다. **등록 성공 거래에서 P의 토큰을 전액 예치하고 그 블록 시각부터 지급을 시작**합니다.

기존 `createSchedule`은 관리자 직접 생성용으로 계속 사용할 수 있습니다. 기존 Sepolia 주소에는 이 새 기능이 없으므로 별도 배포가 필요합니다. 이 문서는 계약과 Foundry 테스트의 로컬 동작을 설명합니다.

## 흐름과 역할

1. P가 토큰을 준비하고 Vesting에 ERC-20 `approve`를 설정합니다.
2. P가 B·총량·cliff·전체 기간·승인 번호·등록 마감·관리자 변경 번호에 서명합니다. 메시지 서명 자체로 자금이 이동하거나 예약되지는 않습니다.
3. B가 조건과 서명을 제출하고 가스비를 냅니다. C가 대신 제출하면 거절합니다.
4. 계약이 조건과 서명을 검사하고 P에게서 토큰을 예치합니다. B는 예치 토큰을 내지 않습니다.
5. 일정 생성과 승인 사용 기록이 함께 확정됩니다. 이후 B는 `claim`으로 받고 관리자는 `revoke`로 취소할 수 있습니다.

B가 14:15에 100토큰·cliff 2분·전체 10분 일정을 등록했다면, 선행 청구 없이 14:17에 20개, 14:20에 50개, 14:25에 100개를 청구할 수 있습니다. cliff는 전체 기간에 포함됩니다. 자동 송금은 하지 않습니다.

## 서명 내용

타입 이름과 필드 순서·타입을 다음 문자열과 정확히 맞춥니다.

```text
ScheduleAuthorization(address funder,address beneficiary,uint256 totalAmount,uint64 cliffDuration,uint64 duration,uint256 nonce,uint256 deadline,uint256 ownerEpoch)
```

| 필드 | 의미 |
| --- | --- |
| `funder` | 서명한 현 관리자이자 실제 제공자. 취소 반환 대상 |
| `beneficiary` | 등록·청구할 수 있는 수령자 |
| `totalAmount` | 최소 단위 총량. 18 decimals의 100토큰은 `100000000000000000000` |
| `cliffDuration` | 등록 성공 후 처음 청구하기까지 잠기는 초 단위 기간 |
| `duration` | cliff를 포함한 초 단위 전체 지급 기간. 0은 불가 |
| `nonce` | 승인 번호. 계약이 부여하는 `scheduleId`와는 별개 |
| `deadline` | 초 단위 Unix 등록 마감. 정각은 허용하고 이후는 거절 |
| `ownerEpoch` | `ownerEpoch()`로 조회할 관리자 변경 번호 |

시작 시각 입력은 없습니다. 제출하거나 지갑에서 확인을 누른 시각이 아니라 **성공 거래가 포함된 블록 시각**으로 결정합니다.

EIP-712 domain은 `name: Vesting`, `version: 1`, 실제 `chainId`, 검증할 Vesting 주소인 `verifyingContract`입니다. 같은 조건의 다른 계약에도 서명을 재사용할 수 없습니다. `eip712Domain()`으로 실제 domain을 조회할 수 있습니다.

`hashScheduleAuthorization`은 domain과 승인 내용을 결합한 최종 해시를 반환합니다. 해시 조회가 마감·사용 여부·자금·권한까지 통과했다는 뜻은 아닙니다. 지갑의 typed-data 서명에는 같은 domain과 타입·메시지를 전달해야 합니다. 해시에 personal-sign 접두사를 다시 붙이는 방식과 다릅니다.

EOA 서명은 ECDSA, 계약 관리자 서명은 ERC-1271로 검증합니다. 계약 지갑의 정책에 따라 같은 서명도 나중에 거절될 수 있습니다. 모든 스마트 계정·EIP-7702 위임 구현을 지원한다는 보장은 아닙니다.

## 중복 사용과 관리자 변경

- 같은 `ownerEpoch` 안에서 각 `nonce`는 한 번만 성공합니다. 8번을 7번보다 먼저 등록해도 됩니다.
- 조건이 같아도 P가 서로 다른 번호로 새로 서명했다면 별도 일정을 만들 수 있습니다.
- 기존 서명에서 번호나 금액만 바꾸면 실패합니다. 바뀐 조건 전체에 대한 새 서명이 필요합니다.
- `ScheduleCreated`는 실제 일정 ID·제공자·수령자·조건을 알립니다. `ScheduleAuthorizationUsed`는 재임 번호·승인 번호와 그 일정 ID를 연결합니다.

관리자 주소가 실제로 바뀌면 `ownerEpoch`가 증가합니다. P→Q→P로 돌아와도 예전 P의 서명은 사용할 수 없습니다. P가 새 재임 번호를 넣고 다시 서명해야 합니다. 승인 번호 자체는 새 재임 번호 안에서 다시 쓸 수 있습니다. 동일 주소로 이전하면 재임 번호를 바꾸지 않습니다. 소유권 포기는 미등록 승인을 무효화하지만 기존 수령자의 청구는 유지합니다.

새 관리자가 기존 일정을 취소해도 반환은 그 일정의 최초 `funder`에게 갑니다.

## 실패와 재시도

승인 사용 기록을 먼저 표시하지만 예치·생성 오류 시 거래 전체가 되돌아갑니다. 자금·approve를 보완하고 **같은 서명으로 재시도**할 수 있습니다. 재시도에도 유효성 조건을 다시 검사하며 성공한 재시도 블록부터 지급합니다.

| 실패 | 남는 상태와 복구 |
| --- | --- |
| 제3자·필드 변경·다른 계약/체인의 서명 | 예치·일정·승인 소비 없음. 지정 수령자가 올바른 조건으로 제출 |
| 마감 경과·이전 관리자 승인 | 미사용이어도 등록 불가. 현 관리자의 유효한 새 승인 필요 |
| 잔고·승인량 부족 | 해당 거래 변경 롤백. 부족분 보완 뒤 마감 전에 재시도 |
| 토큰 revert·false·전액보다 적은 예치 | 사용 기록·예치·유한 승인량 소비도 롤백. 토큰 동작 해결 필요 |
| 등록 중 중첩 등록·청구 | 공통 잠금으로 거절. 오류 전파 시 최초 등록도 롤백 |
| 전송 중 관리자 변경 | 권한 변경까지 포함해 거래 전체 롤백 |

마감 전에 등록한 일정은 마감 후에도 지급합니다. 개별 미사용 승인 철회, 자금 예약, 대리 등록, permit 통합은 제공하지 않습니다. 서명 뒤 제공자의 잔고·approve가 달라지면 등록이 실패할 수 있습니다.

## 테스트 읽기

공통 준비는 시험용 키의 제공자, 별도 수령자, 100토큰 승인, 고정된 테스트 블록 시각입니다. 실제 지갑 키나 네트워크는 사용하지 않습니다. [공통 준비·독립 해시 구성](../test/helpers/SignedVestingTestBase.sol)은 운영 해시 함수로 정답을 만들지 않고 표준 타입과 domain을 직접 인코딩합니다.

| 준비(Given) | 실행(When) | 실제 확인(Then) | 코드 |
| --- | --- | --- | --- |
| 정상 서명·자금·유한 승인 | B 등록 | P -100, 계약 +100, B 0, 제공자=P, 시작=등록 블록, 승인 사용·이벤트 | [등록·서명 테스트](../test/VestingSignature.t.sol) |
| 등록 후 cliff·기간 경과 | 조회와 20→30→50 청구 | 마감 후에도 최종 B=100, 계약=0 | 같은 파일의 시간 경계 사례 |
| 같은 번호/서로 다른 번호 | 재제출/역순 등록 | 같은 번호 거절, 별도 번호로 독립 일정·예치 | 같은 파일의 승인 번호 사례 |
| 다른 계약·체인·키·서명 필드 | 서명 제출 | 검증 오류, 잔고·사용 기록·일정 수 보존 | 같은 파일의 domain·필드 변경 사례 |
| 다양한 총량·nonce | 등록→만기 청구 | 지급 총량 보존, 번호와 일정 ID 독립 | 같은 파일의 두 fuzz |
| approve·잔고 부족 | 실패→보완→원래 서명 재시도 | 최초 변경 없음, 성공 시각에 시작, 마감 뒤 재시도 거절 | [실패 테스트](../test/VestingSignatureFailure.t.sol) |
| 전송 후 false/revert·예치 수수료 | 실패→설정 보완→재시도 | 사용 기록·잔고·유한 승인량·수수료 수신 잔고 복원 | 같은 파일의 토큰 동작 사례 |
| 유효한 수령자 콜백 | 중첩 등록·청구 오류 포착/전파 | 잠금 오류, 최초만 성공 또는 전체 롤백·재시도 | 같은 파일의 콜백 사례 |
| 관리자 이전·복귀·포기 | 옛 승인 등록/기존 일정 청구·취소 | 옛 승인 거절, 기존 권리 유지, 최초 제공자 반환 | [권한 테스트](../test/VestingSignatureAuthority.t.sol) |
| ERC-1271 시험용 지갑 | 정상/거절/revert/짧은 반환/정책 복원 | 예치 또는 서명 오류, 복구 후 같은 승인 등록 | 같은 파일의 계약 지갑 사례 |
| 지갑의 토큰 콜백 | 전송 중 관리자 이전 | 관리자·재임 번호·예치·일정·사용 기록 롤백 | 같은 파일의 전송 중 이전 사례 |

기존 지급 수학·실패·재진입·fuzz·invariant 테스트도 회귀 검사 대상입니다.

```bash
forge test --match-contract 'VestingSignature.*Test' -vv
forge fmt --check
forge build --sizes
forge test --force -vvv
```

Foundry 테스트는 EVM 동작과 시험용 EOA/ERC-1271 검증을 확인합니다. MetaMask의 실제 typed-data 서명 화면과 새 계약 Sepolia 실습은 별도 검증 단계입니다.
